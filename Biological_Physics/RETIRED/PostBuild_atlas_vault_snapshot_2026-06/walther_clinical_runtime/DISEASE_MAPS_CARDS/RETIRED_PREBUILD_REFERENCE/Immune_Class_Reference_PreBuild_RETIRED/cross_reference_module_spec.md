# STEP D2 — Subsection: The Engine Cross-Reference Module

**Proposed addition to STEP D2 of EDEAR_MASTER_ROADMAP.md, after the existing pipeline architecture and before the runtime card schema section.**

---

## The run-everything doctrine (foundational)

Before describing what the cross-reference module does, the doctrine it operates under: **every IDAT runs every atlas, every panel, every per-tile A-score, regardless of any prior-stage result.** Stage 1 Xu-538 immune A-score is computed for every sample. Stage 2 per-tile A-scores against every atlas in the active stack are computed for every sample. Stage 3 immune fine-tune is computed for every sample. Every disease card scores against its own thresholds. There is no conditional gating that skips Stage 2 if Stage 1 is null, no conditional gating that skips Stage 3 if Stage 2 is null. The cross-reference module receives all parallel outputs and produces concordance flags from the joint output, not as a sequential filter chain.

This doctrine is the architectural safety net that surfaces multi-class drift patterns (CCL-035), concurrent-disease scenarios, brain-Moss-gap routing (heme-LL-010), and substrate-distribution-mismatch readings that any conditional pipeline would miss. Run-everything is non-negotiable engine-wide, and the cross-reference module's logic assumes it.

## Stage 2.5 — Cross-reference module (the engine's interpretive layer)

The pipeline as drafted in STEP D2 has eight stages: input validation, IAMAtlas deconvolution, class A-scores, demographic adjustment, range classification, card matching, diagnosis translation, report generation. The cross-reference module sits between Stage 2 (class A-scores) and Stage 5 (card matching) as a Stage 2.5, computing concordance flags that downstream cards can consult during their own scoring without exposing those flags to the customer.

### Why this exists

The cookbook immune-atlas reference document (`immune-atlas v0.3.2`) is the single most operationally important document in the framework. It encodes the expected immune signature for every disease in the catalog (16 entries as of v0.3.2), the five-pattern taxonomy (CCL-031 — pooled-positive, compartment-direction-flip, pooled-null with directional pass, cross-disease direction differences, lineage-confirmed bidirectional cancellation, plus pattern-6 substrate-distribution mismatch and pattern-7 population-fraction-shift), the four Stage-1-positive Stage-2-null diagnostic pathways (terminal-class hidden by specimen problem, hematologic compartment, cardiovascular systemic inflammatory, unexplained immune drift), the CCL-027 four-question protocol, and the cookbook doctrine touching the immune class.

This material is the interpretive intelligence of EDEAR. It is what makes the framework distinguish breast cancer's positive immune signature from CRC's compartment-direction-flip negative blood signal, distinguish AD's bidirectional pattern from a uniform elevation, distinguish cardio's whole-blood-null-but-tissue-positive substrate dichotomy, and so on across all 16 diseases.

In the runtime architecture, this material does not belong in any individual customer-facing card. Forcing it into the v1.0 card schema would either bloat the schema beyond utility or produce a schema that does not actually encode the cross-disease pattern matching that gives the immune-atlas its diagnostic power. The right home is engine code — a module that executes the cookbook immune-atlas's logic at runtime, consuming Stage 2 output and producing concordance flags that downstream cards consult.

### What the module does

For each customer sample, the module operates in two phases: (1) pre-test integrity gating, and (2) pattern matching and concordance flag production. Phase 1 must pass before Phase 2 runs; if any integrity gate fails, the module returns a structured "sample not eligible for concordance" status and downstream cards do not consume any concordance flags for the sample.

#### Phase 1 — Pre-test integrity gating (per cookbook §2.3 and TESTING_CHECKLIST CHK-3.x)

Six gates fire in sequence. Any failure halts pattern matching and produces a structured "integrity-failure" status passed to Stage 5. The customer's report still produces a wellness-class score for cleanly-passing classes; integrity failures on the immune class produce a report that flags reduced confidence on the immune class and recommends retesting.

- **CHK-3.1 raw β distribution sanity.** Bimodal distribution with extremes ≥ X% (substrate-specific threshold). Catches normalized output (residual M-values, noob-bg-corrected betas with additional normalization) that the panel scoring is not calibrated for. Failure mode example: VAL-077 LBC processed-output substrate; VAL-100 EPIC v2.0 noob-bg-corrected supplementary file.
- **CHK-3.1B per-sample atlas coverage.** Per-sample valid CpG count ≥ substrate-floor threshold (≥75% panel coverage default; cohort-specific thresholds per atlas calibration). Catches per-sample QC failures and panel-cohort transferability issues. Failure mode example: VAL-120 TCGA-BLCA Xu-538 51.1% pass rate.
- **CHK-3.1C atlas duplicate audit.** No duplicate CpGs within an atlas's deduplicated CpG set. Atlas-internal sanity check.
- **CHK-3.2 cross-cohort baseline alignment.** Anchor-SD comparison between calibration and customer sample. Off-spec scale flags the sample as potentially mis-formatted; > 1 anchor-SD baseline offset is the gate threshold; > 15 SD is off-spec.
- **CHK-3.5 saturation flag.** Per-sample distance from A_ceiling. Rejects samples saturated against the ceiling that cannot produce meaningful magnitudes.
- **Sex-required gating (CCL-002).** The module refuses to produce concordance flags on a sample with missing sex_at_birth covariate. The score is computed (sex-stratification only affects threshold lookup, not score computation), but concordance is not produced. Recommended customer-facing: "We need to know your sex at birth before we can finalize your immune-class interpretation. Please update your intake."

#### Phase 1.5 — Ten failure-mode fingerprints (per cookbook §2.9)

Before pattern matching, the module checks ten specific failure modes that look like biology but are test failures. When any fires, the module produces a "failure-fingerprint detected" status and the corresponding card-side handling fires (typically: log internally, flag in report as test-quality issue, recommend retesting, do NOT produce a concordance flag). The ten fingerprints are: (1) bulk-WGBS-on-mucosal-substrate inflation (Pattern 6 anchor); (2) supplementary-file-vs-raw-IDAT scale mismatch (VAL-077/100 anchor); (3) HC-mean cohort batch offset (VAL-057 GSE53740 +2.306 SD anchor); (4) cross-platform NNLS routing artifact (VAL-091 AddNeuroMed +7.4% cortical-neuron HC anchor); (5) panel-coverage substrate-transferability failure (VAL-076 LBC-Xu-538 anchor); (6) cohort-direction-flip from HPV-negative-normal anchor selection (VAL-074 anchor); (7) cultured-cell methylation drift simulating biology (VAL-109 PEC anchor); (8) tumor-immune-infiltrate vs adjacent-normal contrast simulating tile biology (VAL-097 baseline-dominated anchor); (9) gene-promoter atlas tile-discrimination collapse (VAL-094/111 anchor); (10) population-fraction-shift on sorted-cell substrate erroneously read as null (VAL-128 mixture-attenuation reversal anchor). Each fingerprint has a documented detection rule keyed to the sample's metadata + Stage 1/2/3 outputs.

#### Phase 2 — Pattern matching and concordance flag production

After Phase 1 and Phase 1.5 pass, the module performs:

**Pattern matching against the disease signature catalog.** For each of the 16 diseases in the cookbook immune-atlas, the module checks whether the customer's immune signature is consistent with that disease's expected pattern. The check returns a concordance score (low / moderate / high) indicating how much the customer's immune signal looks like that disease's predicted Stage 1 fingerprint. This is not a disease prediction — it is a pattern match that informs how the corresponding disease card should interpret its own Stage 2 organ tile signal.

**Pathway routing per CCL-027 four-question protocol.** When Stage 1 is positive (immune class elevated above the customer's range threshold) but Stage 2 returns no localized organ-tile signal, the module routes the case through the CCL-027 four-question algorithm to determine which of the four pathways applies: terminal-class hidden by specimen, hematologic compartment, cardiovascular systemic inflammatory, or unexplained drift requiring trajectory monitoring. The routing produces an internal pathway tag.

**Pattern taxonomy classification per CCL-031.** The module classifies the customer's immune pattern into one of the seven CCL-031 patterns: pooled-positive, compartment-direction-flip, pooled-null with directional pass (AD-instance), cross-disease direction difference, lineage-confirmed bidirectional cancellation, substrate-distribution mismatch on mucosal cohort, or population-fraction-shift signature. The pattern tag is engine-internal context, not a customer-facing label.

**Bidirectional consistency check.** The module evaluates the directional consistency of immune-class CpGs and produces the bidirectional flag that informs downstream cards (specifically AD-immune which fires on this pattern via its directional 7-CpG Rule A panel, and pancreatic-epic which fires on the same pattern via its 324-CpG directional panel).

**Substrate-distribution-mismatch check.** When multi-atlas Stage 2 readings disagree at high magnitude in opposite directions (Pattern 6), the module flags this as substrate-distribution-mismatch rather than as biology, and the disease card consuming the flag knows to interpret the gene-promoter atlas reading as the headline rather than the bulk-WGBS reading.

**Population-fraction-shift detection.** When Stage 1 is null across all cell-type strata but Stage 3 cell-fraction deconvolution shows bidirectional shifts (T-cell expansion + myeloid depletion or vice versa), the module flags this as Pattern 7 and the corresponding cards (Crohn's/IBD pathway when added; chronic viral infection cards when added) consume the flag.

**Field-effect adjusted comparisons (CCL-008).** When the module evaluates a customer sample against a tumor-vs-adjacent-normal research anchor, it accounts for the cookbook's documented field-effect: TCGA adjacent-normal tissue is itself architecturally elevated by a substantial fraction of the tumor signal (research mean ΔA_field ≈ +0.036, 22.9% of tumor signal across 24 cancer types per VAL-037). The module's anchor-magnitude lookup tags each anchor with whether the comparator was true-healthy, adjacent-normal, or tumor-vs-different-tissue, and concordance scoring weights anchors accordingly. This prevents the engine from interpreting "modestly elevated vs adjacent-normal anchor" as identical to "modestly elevated vs true-healthy anchor."

**Multi-class drift detection (CCL-035).** When Stage 2 produces concordant elevation across multiple non-immune tiles in the apparent absence of localized single-tile dominance — pancreatic tile elevated AND kidney tile elevated AND colon tile elevated, none dominant — the module produces a "multi-class drift" concordance flag rather than a single-tile localization flag. This is the VAL-093 >10yr breast pre-dx signature, where the breast tile itself reads NULL while pancreatic and cycling-class tiles concordantly elevate. The downstream report framing is the trajectory product framing (Scenario 6 on the immune website page), not single-disease attribution.

**Comparison-type direction handling (CCL-039).** Cell-of-origin tile direction expectation depends on what the comparator is. Tumor-vs-adjacent-normal expects a different direction than tumor-vs-different-tissue (e.g., bladder cell-of-origin tile reads NEGATIVE in tumor-vs-adjacent-normal because urothelial-program loss in tumor; same tile reads differently in tumor-vs-different-tissue). The module's anchor table tags each anchor with comparison type and the concordance scoring uses the type-appropriate direction expectation, not a single global direction.

**Brain-cancer Moss-gap routing (heme-LL-010).** When Stage 1 fires positive AND Stage 2 returns Moss-NULL across all 18 peripheral solid-tissue tiles, the module does NOT route to "definitely heme." It routes to Pathway 1 (terminal-class hidden by specimen) candidate AND emits a brain-Moss-gap warning. The Moss reference does not include CNS tissue because the blood-brain barrier limits cfDNA fraction from primary CNS tumors; "Moss-NULL on solids" rules out 18 peripheral tissues but does NOT rule out CNS disease. The corresponding card-side handling is to surface "neurological evaluation candidate alongside other differentials, not confirmation of heme cancer" rather than a heme-only routing.

**Glioma-vs-AD differential-diagnosis-required flag (VAL-091 anchor).** A specific case of the brain-Moss-gap rule: when Stage 1 immune-class A-score fires positive AND Stage 2 cortical-neuron tile reads > 0.5%, the module emits a DIFFERENTIAL_DIAGNOSIS_REQUIRED flag. This combination is more consistent with glioma (research anchor cortical-neuron 1.09% per VAL-090) than with AD (research anchor cortical-neuron 0.25% per VAL-091) at 450K-array NNLS resolution. The customer's report surfaces the combination directly and recommends physician review of the specific pattern, not a single disease attribution.

**HPV stratification routing (cerv-LL-002).** HPV is a STAGE 1 STRATIFIER for cervical-pattern interpretation, not metadata. When the module evaluates cervical-pattern concordance, it routes through HPV-specific threshold tables: HPV-negative healthy baseline differs from population-normal baseline (VAL-074 anchor: HPV-negative healthy cervical tissue reads 2.7 anchor-SD lower than population-normal cervical tissue). Without HPV status declared, the module emits a "HPV-stratification-required" status for cervical-pattern matches; concordance is not produced for cervical patterns until HPV status is intake-complete.

**Substrate-scope output tagging (heme-LL-009).** Each concordance flag the module produces is tagged with the substrate scope of its anchor evidence: methyl-only single-substrate buffy-coat (the v1 deployment regime, the default for almost every current anchor), methyl-only single-substrate plasma cfDNA (VAL-059 ccfDNA anchor scope), tissue-substrate research only (TCGA-derived anchors), or 5-substrate combined cfDNA (Issue 002 framework predictions for L2/L3 future platform expansion, NOT directly comparable to v1). Downstream cards know to interpret v1-tagged magnitudes per v1 deployment expectations and not against Issue 002 5-substrate predictions. Without this tagging, the engine could compare an Issue 002 prediction (A_AML ≈ 1.10) to a v1 magnitude (ΔA = +0.10 absolute) as if they were the same regime; they are not.

**Stage 1 deployment-scope tagging.** Each concordance flag is also tagged with the validated Stage 1 deployment scope: validated-positive (e.g., advanced cancer plasma cfDNA per VAL-059; pre-diagnostic cancer blood per VAL-047), validated-NULL (chronic inflammatory disease per VAL-128, AD without directional panel per VAL-050, PDAC without directional panel per VAL-066-068), or out-of-scope (the customer's substrate is outside any documented deployment scope). Downstream card behavior depends on this tag: validated-positive cards score against full thresholds; validated-NULL cards run the appropriate directional sub-panel before producing concordance; out-of-scope cards report reduced confidence.

**Stage 3 atlas role differentiation.** The module differentiates the three Stage 3 atlases by query-purpose. **Salas Blood.EPIC IDOL 6-cell** is the production Stage 3 atlas — every sample reads against it for the 6 immune lineage proportions. **UniLIFE Guo 2025 19-cell** is queried specifically for resolution-gain at long pre-diagnostic windows (the aTreg signal at >10yr breast pre-dx is the canonical case) and for adult-specific subtype resolution (aCD4Tnv, aCD8Tnv, aBnv, aBmem, aCD4Tmem, aTreg, aMono, aNeu, aEos, aBaso) where Salas 6-cell aggregates collapse the signal. UniLIFE adds little at near-diagnosis windows where Salas 6-cell suffices. **Caggiano CelFiE TIM** is queried for tissue-of-origin coverage (heart tile, endothelial, fibroblast cell types in the stromal class; hepatocyte and mammary in the secretory class; lung and small intestine in the cycling class; brain/heart/skeletal in the terminal class; megakaryocyte/erythroblast in the progenitor class) plus immune subtypes (dendritic, eosinophil, macrophage, monocyte, neutrophil, tcell) where neither Salas nor UniLIFE provides the relevant cell-type tile. The module routes the right atlas to the right question rather than running them all redundantly on every question. Class-assignment discipline applies: megakaryocyte and erythroblast are progenitor-class cell types per the canonical cell-type inventory, even though they appear in the Caggiano TIM atlas alongside immune subtypes — Caggiano's atlas mixes lineages and the harmonization at MCMC time routes each cell to its correct architectural class.

**Pathway 1-4 decision algorithm (cookbook §9 routing).** Pathway routing per CCL-027 four-question protocol is encoded as actual decision logic, not just mention:
- **Pathway 1 (terminal-class hidden by specimen):** Stage 1 weakly-to-moderately positive + Stage 2 returns null on all peripheral tiles + Moss reference does not cover the candidate tissue (CNS, certain rare tissues) + (optionally) customer reports neurological symptoms or relevant family history. Routing produces "Pathway 1 candidate; recommend neurology consult, CSF if indicated, AD trajectory watch."
- **Pathway 2 (hematologic compartment):** Stage 1 strongly positive + Stage 2 null on solid organs + Stage 3 lineage signature fires (neutrophil-dominant or B-cell-dominant or T-cell-dominant or uniform-elevation). Routing produces "Pathway 2 candidate; recommend CBC with differential, hematology consult."
- **Pathway 3 (cardiovascular systemic inflammatory):** Stage 1 positive + Stage 2 cardio-tile signal (heart, vascular endothelial, adipocyte, pulmonary endothelial) + customer covariates indicate cardiovascular risk (age, sex, smoking, BMI, hypertension, diabetes). Routing produces "Pathway 3 candidate; recommend cardiovascular workup."
- **Pathway 4 (unexplained immune drift, trajectory watch):** Stage 1 positive + Pathway 1/2/3 do not fire. Routing produces "Pathway 4; recommend trajectory monitoring at 3-6 month interval."

**Mahalanobis differential ranker.** For samples that produce a multi-class concordance fingerprint (the customer's pattern matches multiple disease signatures partially), the module computes a Mahalanobis distance from the customer's pattern to each disease signature's centroid in the cookbook catalog. The ranker outputs an ordered list of "best-matching" patterns with distance metrics, used by downstream cards to weight their threshold lookups. Importantly, this is engine-internal — the customer never sees a "your pattern is X% breast, Y% pancreatic" attribution. The ranker informs how each card interprets its OWN signal in the context of the customer's overall pattern, not a customer-facing differential diagnosis.

**Card-readiness check (CCL-029 cohort-completeness gate).** Before producing concordance for a disease pattern, the module verifies the cookbook has marked the pattern's underlying card as cohort-complete (v0.1 publish-ready or beyond). For cards still pending cohort completion, the module emits "card-readiness-incomplete" status and the corresponding pattern is not consumed by downstream interpretation. This prevents premature deployment of disease-specific concordance from cards that have not finished their validation breadth.

### What the module does not do

The cross-reference module never produces customer-facing output. The customer sees the per-card findings that result from the cards consuming the engine's concordance flags. The customer does not see "your immune signature is consistent with the breast cancer pattern" because that statement would be (a) an overclaim from a single time-point measurement, (b) not aligned with the wellness positioning, and (c) not what the framework can honestly claim from a single sample.

The module also does not gate which cards run. All cards run in parallel per the run-everything doctrine. The module's output is enrichment context for card interpretation, not a routing decision.

### Implementation outline

The module is a Python class loaded at server startup alongside the IAMAtlas, the card library, and the GAPE engine. Its constructor reads the cookbook immune-atlas v0.3.2 JSON (or its successor) at startup and parses the disease_signature_catalog, the ccl_027_four_questions_master_table_v0_3, the ccl_031_five_pattern_taxonomy_v0_3, the stage_1_positive_stage_2_null_pathways, and the relevant cross-reference structures into in-memory pattern-matching tables.

At runtime, for each sample, the module receives Stage 2 output (immune class A-score, per-cell-type fractions, bidirectional consistency flag, optional Stage 3 cell-fraction deconvolution if available) plus customer covariates (smoking bin, recent illness, vaccination, etc.) and produces a concordance object passed to Stage 5 (card matching). Each card's threshold-lookup logic consumes the relevant fields of the concordance object — most cards consume just one or two flags, the immune wellness card consumes the bidirectional flag for its bidirectional firing rule, complex cards like ad-immune and pancreatic-epic consume the directional-pass flag, and cards for diseases with substrate-distribution-mismatch sensitivity (bladder, gastric, esophageal, cervical) consume the Pattern 6 flag.

The module is engine code, not card content. It lives in the EDEAR engine module structure, probably as `edear_engine/cross_reference.py`. The cookbook immune-atlas JSON is its source of truth — when the cookbook immune-atlas is amended (a new disease added, a new pattern sealed, the catalog extended), the new content is automatically picked up at the next server restart. No engine code changes required to add new diseases — the cookbook immune-atlas update plus a new runtime card JSON in `cards/` is all that's needed.

### IP protection

The cookbook immune-atlas content used by the module is interpretation logic — disease pattern signatures, directional indicators, bidirectional detection, pattern taxonomy. None of this contains the IAM physics derivation, H_min calibration logic, or Mahaffey Number computation. The cross-reference module reads the cookbook immune-atlas as a structured-pattern lookup, not as a physics derivation. The cookbook immune-atlas itself is Heath-only IP and is not deployed to the public repo — it lives in the project files. The module references it at runtime through a private path that is not in the public repo. The engine source code on the public repo would reference an abstract pattern-table loader interface; the actual cookbook content is loaded from a private location at server startup.

### Why this architecture is right

The cross-reference module gives the engine the cookbook's interpretive intelligence without forcing that intelligence into customer-facing cards. Customer cards stay minimal (six functional fields plus four flag-summary strings, ~50-100 lines per card). The engine carries the heavy interpretive lifting. The website carries the customer-facing educational content. Three layers, three responsibilities, clean separation.

When new diseases are added to the catalog, the work is: amend the cookbook immune-atlas with the new disease's signature and pattern; add a new minimal runtime card to `cards/`; add a new educational page on the website. The engine code does not change. This is exactly the modularity the wellness-first positioning's KISS principle requires.

When the framework's understanding of patterns evolves (new patterns identified, existing patterns refined, validation evidence updates), the work is: amend the cookbook immune-atlas; restart the server. No card changes, no engine changes. The cookbook immune-atlas is the single source of truth for cross-disease interpretation logic, and updating it propagates everywhere automatically.

This architecture also means the cookbook immune-atlas v0.3.2 work — the 1500+ lines of carefully built interpretive material — is preserved as a runtime asset rather than being orphaned as a pre-engineering artifact. The work that built the cookbook is exactly the work that powers the engine's interpretive intelligence at runtime.

### Open questions for engineering review

1. **Cookbook immune-atlas JSON parsing.** The cookbook immune-atlas v0.3.2 has 38 top-level keys with nested structures including the disease_signature_catalog (16 entries), ccl_027_four_questions_master_table_v0_3 (5 sub-keys), ccl_031_five_pattern_taxonomy_v0_3 (7 sub-keys), and others. The parsing needs to extract the runtime-relevant fields without assuming the cookbook structure stays static across versions. The parser should be tolerant of minor schema drift and explicit about which fields are required vs optional.

2. **Module update cadence.** When the cookbook immune-atlas is amended (e.g., v0.3.3 with a new disease signature added), should the engine pick up the change automatically at next server restart, or should there be an explicit version-pinning mechanism so production engines don't pick up amendments without a controlled deployment? Recommendation: explicit version pinning. Engine config specifies which cookbook version to load. Amendments require a config change and intentional restart, not just file presence.

3. **Performance considerations.** Pattern matching across 16 diseases × 7 patterns × 4 pathways for each customer sample is roughly 100-1000 simple checks. Negligible compute overhead. The module loads the cookbook immune-atlas once at startup and operates on in-memory tables thereafter. No bottleneck concerns.

4. **Stage 3 readiness.** The cookbook immune-atlas references Stage 3 (lymphoid-vs-myeloid sub-panel split via OQ-2026-01) which is not yet operational. The module should encode the Pattern 5 detection logic (lineage-confirmed bidirectional cancellation) but return a structured "Stage 3 not yet operational" flag rather than firing pattern-5 detection until OQ-2026-01 lands. When Stage 3 becomes operational, no module code changes are required — the cookbook immune-atlas amendment that promotes Stage 3 from pending to operational is what flips the gate.

5. **Cross-card synthesis pairs.** The cookbook immune-atlas v0.3.2 has cross_card_synthesis pairs (gastric_vs_esophageal, crohns_vs_everything, gastric_vs_bladder, esophageal subtype discrimination). These are higher-order pattern matches across pairs of disease cards. Should the cross-reference module evaluate these pair-wise synthesis tags and emit them in the concordance object, or should pair-wise synthesis be a separate engine module? Recommendation: include in cross-reference module for now (it is the same kind of pattern matching). Promote to separate module only if the synthesis catalog grows substantially.

### Exit gate for the cross-reference module

A unit test suite that, given synthetic Stage 2 output for each of the 16 diseases at typical pre-diagnostic and at-diagnosis magnitudes, produces concordance objects whose flags match the cookbook immune-atlas's expected patterns. Plus a synthetic test where the customer's immune signal is null on aggregate but has bidirectional consistency: the module returns a bidirectional flag at the right level for ad-immune and pancreatic-epic to consume. Plus a synthetic test where the customer's pattern matches Pathway 4 (unexplained drift): the module returns the correct routing tag without producing a disease-specific concordance.

When the test suite passes for every cookbook immune-atlas pattern, the module is ready. Cards that consume concordance flags are then validated individually against their own card-specific test cases.
